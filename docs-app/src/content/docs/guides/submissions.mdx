---
title: Submissions Inbox
description: Work, email, export, and retain permission-scoped CoreX flow responses safely.
---

Open **CoreX → Submissions** to work with the responses stored by published flows. The Inbox is distinct from the raw
Data explorer: it owns team workflow, personal-data controls, related email actions, and the submission timeline.

## Find and work a response

Search by submitter or flow and combine flow, status, owner, and date filters. Marked tests are hidden by default; turn
on **Include marked tests** only when diagnosing the real seven-stage flow pipeline. Every list count and detail request
uses the current actor's record scope, so inaccessible records do not leak through counts, filters, or direct IDs.

Click anywhere on a row, or press Enter on it, to open the submission in a pane beside the list. The row that is open
stays marked. Escape or **Close** shuts the pane and puts focus back on the row.

The pane reads from the top down:

- **The header**: the sender's name, their email address and phone number as links when the form asked for them, the
  form, the submission's number, when it arrived, its status, and whether it is read.
- **Answers**, each under the question the form asked. An answer to a question the form no longer asks is kept, under
  the key it was stored with.
- **Reply** and **Team notes**.
- **Triage**: the status, and **Assigned to**, which lists the people who can manage submissions, and Unassigned.
- **Notification**: what became of the notification, when, and the reason when one was recorded.
- **Technical details**, closed until opened: hidden fields, campaign data and the consent record, whichever of them
  the submission holds. A submission that holds none of them says so on one line.
- **History**, closed until opened: what happened to the submission, and when.

Opening an unread submission marks it read. **Mark unread** in the header puts it back, for somebody who only looked.

Change the status to New, In progress, Replied, Closed, Spam, or Archived. Read, status, and assignment writes are
optimistic: if another teammate changed the response after it loaded, CoreX returns a conflict and asks the Inbox to
refresh instead of overwriting their work.

## Bulk actions

Select up to 100 visible rows, then preview Mark read, Assign, Mark spam, or Archive. The preview is bound to your user,
the exact selected IDs, and their update timestamps; it expires after five minutes and can be applied once. If any row
changes or becomes inaccessible, the whole action stops before mutation rather than silently applying a partial result.

## Notification delivery

Every row shows the notification outcome of its submission, and the pane repeats it with a safe reason and the time it
was attempted. The states are distinguished by text and icon, never colour alone:

- **Notification accepted** — the mail path accepted the message for delivery. This is *not* proof it reached an inbox.
- **Notification captured** — a development capture stored it instead of sending externally.
- **Notification queued** — a real queue accepted the job; delivery has not completed.
- **Notification failed** — an attempted delivery failed. A resend may be available.
- **Notification rejected** — routing, policy, or configuration prevented an attempt.
- **No notification** — none was required or configured for this form.
- **Not tracked** — no delivery was recorded for the submission. A form defined in code sends its notification without
  recording it, so every one of its submissions reads this way; so does a submission stored before delivery was
  tracked. The pane says which.

A saved submission with a failed notification is still saved and still readable — the failure is surfaced, never hidden.
The timeline records a **notification** event alongside the submission event, so the outcome is visible in the history.

## Reply and inspect delivery

When the submission contains a valid email address and Email Studio is active, the pane can send a reply. A related
retryable template attempt can be resent from its immutable template version and current submission context. **Open
log** returns the redacted delivery record only when that attempt belongs to the open submission. Development captures
these messages; Staging and Production still follow Email Studio's provider and live-delivery gates.

## Export personal data

Choose **Export**. Under **What to export**, pick one, each shown with how many submissions it holds:

1. **Selected rows**: only the rows ticked in the inbox.
2. **Current filters**, spelled out: the form, status, owner, dates and search in force.
3. **Everything** you can access.

Under **Columns**, choose the groups to include: Submission details, Status and assignment, Answers, Hidden fields,
Campaign data, Consent record, Team notes. The file has one row per submission and one column per answer, headed by
the question the form asked. Personal-data columns require both the export permission and an explicit
acknowledgement. Marked tests remain excluded unless you tick **Include submissions marked as tests**.

Under **Format**, choose **Excel workbook (.xlsx)**, **CSV (.csv)** or **PDF document (.pdf)**. A workbook has a sheet
per form, real dates and numbers, and a frozen heading row. A CSV opens correctly in a spreadsheet, with a choice of
separator: comma, semicolon or tab.

A PDF is a document to keep or print, on A4 pages set wide. It opens with what was exported, how many submissions, and
who exported it and when. Every page is headed by the site's name and the export's title, and signed at the foot with
the CoreX logo, "Exported with CoreX", the copyright line and the page's number out of how many. The heading row is
repeated on each page. An export of more than eight columns is set out one submission at a time, each question beside
its answer, because that many columns do not fit a page. On a right-to-left site the page reads right to left, and a
phone number, a date or a Latin-script answer inside it keeps its own order.

A PDF holds up to 500 submissions. The dialog says so under the choice, and names the limit instead of starting when
the choice holds more: export fewer, or choose a workbook. On a site installed from the shared-host package, text in a script whose font the package was built without
prints as empty boxes in a PDF; the workbook and the CSV hold it as it is (see the shared-host package's
`--pdf-fonts`). PDF is offered only where the server can write one, which
needs PHP's `gd` and `mbstring` extensions.

The dialog shows the export's progress and saves the file when it is ready; there is nothing to refresh. History
records the actor, scope, columns, row count, and time, while the shared activity stream records the compliance event
without copying submitted values.

### Recent exports

Under the form, **Recent exports** lists what was exported before: your own exports, or everybody's when you may
manage every submission. Each entry says what it covered (the ticked rows, the filters in words, or everything), its
format, how many submissions, how large the file is, who made it and when, and what became of the file:

- **Expires** on a date: the file is kept, and **Download** saves it again.
- **Expired**: the file passed its retention and can no longer be downloaded. The entry stays.
- **Deleted by** somebody, on a date. The entry stays.
- **No file to download**: the export did not finish, or its file is no longer on the server.

An exported file is kept for 30 days from the day it was made. The daily retention sweep then removes the file and
leaves the entry. **Delete** removes a file sooner, after asking; the activity stream records who deleted it. The list
shows the five newest; a link under them, which says how many more there are, shows the rest.

In a CSV, a value that begins with `+`, `-`, `=` or `@` is written so a spreadsheet does not run it as a formula.
Downloads pass through the authorized Inbox endpoint rather than exposing a public uploads URL.

## Retention

Set the age window under **Submission retention**. The panel shows how many responses are currently due: older than the
window and still holding their personal data. The count excludes marked tests by default and stops at 500, the size of
one run. After confirming, choose one operation:

- **Archive** keeps the response and marks its workflow and retention state.
- **Move to trash** uses WordPress's recoverable trash.
- **Anonymize personal data** removes submitted values, submitter projections, hidden/UTM/consent data, and notes while
  preserving non-personal workflow evidence.

A run handles at most 500 responses, oldest first, and skips the ones its operation has nothing left to do for:

- An anonymized response is finished. It is no longer counted as due, and no operation selects it again.
- An archived response still holds its personal data, so it stays in the count and can still be anonymized or moved to
  trash. Archive does not select it a second time.

Each applied archive or anonymization writes a retention timeline event. Including marked tests is a separate explicit
choice so diagnostic fixtures are never swept into ordinary retention work accidentally.
