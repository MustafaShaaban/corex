# Feature Specification: An Extendable User-Guide Add-on

**Feature Branch**: `spec/084-guides-addon`

**Created**: 2026-07-28

**Status**: Draft

**Input**: Owner direction — *"for the guide I think we need to create it as an add-on… the same
add-on will be extendable for any website created using corex to add its user guide to it. For
example now corex framework has its user guide for admin dashboard. Perego will extend the same
add-on to add its guides for new post types for example or any new features or flows added by the
website."*

**Supersedes**: `specs/082-dashboard-user-manual`.

## Why this spec exists, and why 082 is not it

Spec 082 designed a manual: Markdown in a docs tree, screenshots generated by Playwright, explicitly
*"this spec does not change any product code"*. It has no extension seam of any kind, and its own
open decision #1 is where the file should live.

That is the wrong shape for what is actually needed, for two reasons.

**A site's guide cannot live in the framework's docs tree.** Perego's guides are about Perego's post
types and Perego's flows. They ship with Perego, they version with Perego, and they must appear
without anybody editing CoreX. A Markdown file in `docs-app/` can express CoreX's manual and can
never express a client's.

**The manual is needed where the work happens.** 082's own US3 says *"the manual is where they would
look — and the spec must decide where that is."* For somebody handed a finished site, the answer is
wp-admin, not a documentation website they were never told about.

So the deliverable is an **add-on that owns a guide registry**. CoreX registers its own guides
through it. A site plugin registers its own through the same public API. Both render on the same
screen, and neither knows about the other.

## What carries over from 082

The content requirements are good and are kept: numbered steps that name the control and the
expected result (FR-001–FR-005 there), a warning before anything hard to undo, no control documented
that does not exist, and screenshots produced by a capture script driving the real admin so they
cannot drift (082 FR-006–FR-010). What changes is where the content lives and who can add to it.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Somebody handed a finished site finds out how to use it (Priority: P1)

A non-technical site owner opens their admin, finds a Guides screen, and reads how to do the thing
they came to do — read a submission and answer it, publish a post, check whether an email went out.

**Independent Test**: open the Guides screen as an administrator on a stock CoreX install and follow
one guide end to end without leaving wp-admin.

### User Story 2 — A site adds its own guides without touching CoreX (Priority: P1)

Perego's own plugin registers guides for its post types and flows. They appear on the same screen,
grouped with CoreX's, and survive a CoreX upgrade because nothing in CoreX mentions them.

**Why this priority**: it is the reason this is an add-on rather than a docs page. Without it the
whole spec collapses back to 082.

**Independent Test**: a second plugin registers a guide from its own service provider; the guide
appears; deactivating that plugin removes it and leaves the screen intact.

### User Story 3 — A reader is never shown a screen they cannot open (Priority: P1)

Guides for add-ons that are not active, or for screens this user lacks the capability for, are not
listed at all.

**Why this priority**: 082 names this as an edge case and has no mechanism for it. A manual that
documents absent screens teaches people the product is broken.

### User Story 4 — Help is one click from the screen it describes (Priority: P2)

A guide that names the admin screen it belongs to also appears in that screen's contextual help tab.

**Why this priority**: the WordPress contextual-help API is used **zero times** in this repository
today, so this is a whole surface standing empty.

## Requirements *(mandatory)*

### The registry

- **FR-001** A public `GuideRegistry` MUST accept guides from any plugin, with `register()` for
  immediate registration and `registerDeferred()` for guides that cannot be built at call time.
- **FR-002** Registration MUST be safe from any plugin loading at any point up to first read. CoreX
  boots on `plugins_loaded`; a site plugin registering on the same hook must not lose a race.
- **FR-003** The registry MUST resolve deferred factories exactly once, on first read, and MUST NOT
  recurse if a factory reads the registry back.
- **FR-004** A `corex_guides` filter MUST provide a second seam for callers with no container
  access, and anything it returns that is not a guide MUST be discarded rather than rendered.
- **FR-005** Registering the same guide id twice MUST replace rather than duplicate, so a site can
  override a CoreX guide it disagrees with.

### The content model

- **FR-006** A guide MUST carry an id, a title, a summary, a section for grouping, and an ordered
  list of topics; a topic MUST carry an id, a title and ordered steps.
- **FR-007** A step MUST be able to name the control, state the expected result, and optionally
  carry a warning and a screenshot.
- **FR-008** A guide MUST be able to declare the admin screen it describes and the capability a
  reader needs.

### Availability

- **FR-009** A guide whose declared capability the current user lacks MUST NOT be listed.
- **FR-010** A guide contributed by an add-on that is not active MUST NOT be listed. The add-on's own
  provider is the natural place for that to be true by construction.

### The surface

- **FR-011** A Guides screen MUST list every available guide grouped by section, and open a topic's
  steps.
- **FR-012** The screen MUST be searchable across registered titles and step text, with no external
  dependency.
- **FR-013** A guide declaring a screen MUST add a contextual help tab on that screen linking to it.
- **FR-014** The screen MUST follow the CoreX admin shell: tokens only, logical properties, RTL, and
  WCAG 2.2 AA.

### Screenshots

- **FR-015** Screenshots MUST be produced by a capture script driving the real admin, regenerated by
  one documented command, and MUST fail loudly when an expected screen or control is missing.

### Extension documentation

- **FR-016** The public extension API MUST be documented with a working example a site developer can
  copy, and a `wp corex make:guide` generator MUST scaffold one.

## Success criteria

- **SC-001** A second plugin registers a guide on `plugins_loaded` at default priority and it appears
  — the boot race, tested rather than reasoned about.
- **SC-002** A guide requiring a capability the viewer lacks is absent from the screen and from the
  help tab.
- **SC-003** Deactivating a contributing plugin removes only its guides.
- **SC-004** A malformed contribution through the filter is discarded and the screen still renders.
- **SC-005** Changing an admin screen and regenerating produces a different committed screenshot.

## Assumptions

- The registry copies `DataRegistry`'s shape (`plugins/corex-config/src/Data/DataRegistry.php`),
  which exists because this exact boot-ordering bug was made once already and is documented in its
  own docblock.
- Availability gating follows `NotificationProducerRegistry::isAvailable()`, and add-on guides are
  registered from the add-on's own provider — so an inactive add-on contributes nothing without any
  conditional logic.
- Screenshots are captured with the harness spec 076 established
  (`tests/e2e/capture-datetime-evidence.mjs`), not a new one.

## Out of scope

- Translating CoreX's own guide content. The strings are translation-ready; producing an Arabic
  catalogue is separate work.
- Migrating `docs-app/` or `docs/en/`. This add-on is the in-admin surface; the docs site keeps its
  own job.
- A visual editor for guides. Guides are code, registered by developers.
